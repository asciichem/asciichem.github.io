AsciiChem is a **contract**, not a codebase. The contract has two
halves: the [wire form](/models/) (asciichem-model — versioned JSON
Schemas plus generated types) and the [conformance corpus](/models/#conformance)
(asciichem-tests — the fixtures every implementation must pass in its
own CI). Anything that passes both *is* AsciiChem.

This is the single-contract rule, with the order made explicit: there
is no per-language parser. Every runtime parses through **parsanol
over the one checksummed PARG artifact** of the grammar, and
[asciichem-rs](https://github.com/asciichem/asciichem-rs) is the
**authoritative implementation** — all runtimes carry identical
functionality, and where a port is still pending the matrix below
says so plainly.

## Picking an implementation

- **Documents and standards pipelines (Ruby)** — the gem integrates
  with Metanorma-style publishing; CML round-trip for interchange;
  the CLI covers parsing, rendering, linting, resolving, validation.
- **Systems, CLIs, and services (Rust)** — the authoritative crate:
  the whole surface as a library plus the `asciichem` binary, with
  InChI identity derived in-process (no FFI seam) and networked
  resolution on `ureq`.
- **Web and interactive tools (TypeScript)** — parse and draw
  chemistry client-side; the corpus guarantees the same acceptance as
  every other runtime, so your web previews match your build-time
  renders.
- **Data and science workflows (Python)** — zero-dependency parsing
  into plain dataclasses; wire JSON in and out for pipelines.

All implementations speak the same wire form, so structures move
freely between ecosystems. Conformance is claimed per
[level](/guides/conformance-levels/), not per vibe. The TypeScript
and Python resolver, citation, and linter ports are tracked openly
([asciichem-ts#26](https://github.com/asciichem/asciichem-ts/issues/26),
[asciichem-py#19](https://github.com/asciichem/asciichem-py/issues/19))
— until they land, those layers live in Rust and Ruby.
